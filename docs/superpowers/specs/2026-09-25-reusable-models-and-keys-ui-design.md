# Переиспользуемые страницы моделей и виртуальных ключей

## Цель

Обеспечить стопроцентный функциональный паритет старого и нового интерфейсов ровно для двух страниц:

1. «Виртуальные ключи»
2. «Модели и эндпоинты»

Новый интерфейс сохраняет собственный дизайн «Фокус». Старый и новый интерфейсы используют одну реализацию бизнес-функций, запросов, прав доступа, форм и действий, чтобы следующие обновления upstream не приходилось переносить вручную дважды.

## Границы

В scope входят только функции, доступные на старых страницах виртуальных ключей и моделей с эндпоинтами на зафиксированном upstream `c19ce71bcdad234ca87a7af10cee45375ce811a8`.

В scope не входят остальные страницы dashboard, изменение backend-контрактов, новые бизнес-функции сверх upstream, визуальное копирование старого интерфейса и изменение выбранной компоновки «Фокус».

Технические имена моделей, провайдеров, API, LLM, HTTP-коды и конфигурационные поля не переводятся. Видимые подписи, подсказки, уведомления, ошибки и пустые состояния имеют пары EN/RU. Видимый бренд LiteLLM заменяется на Nexoplane, технические идентификаторы сохраняются.

## Основной принцип

Функциональность принадлежит общему слою, а не конкретной странице.

Общий слой отвечает за:

- запросы и мутации;
- состояние URL, фильтров, сортировки и пагинации;
- права доступа и доступность действий;
- схемы форм и построение payload;
- статусы, вычисляемые значения и обработку ошибок;
- открытие, сохранение, удаление, приостановку и возобновление сущностей;
- актуальный набор возможностей upstream.

Старый UI отображает общий слой таблицами и существующими панелями. Новый UI отображает те же данные и действия карточками, вкладками и правой панелью «Фокус». Визуальные компоненты не содержат собственных сетевых вызовов или отдельной бизнес-логики.

## Виртуальные ключи

### Общая функциональная основа

`useKeys`, `useKeyInfo`, `CreateKey`, `KeyInfoView` и общие query keys остаются единственными реализациями загрузки списка, создания ключа и деталей ключа.

Состояние списка выносится в общий контроллер страницы виртуальных ключей. Он предоставляет:

- строку поиска;
- фильтры команды, организации, пользователя, идентификатора ключа и статуса;
- сортировку по имени, идентификатору, датам, расходу и бюджету;
- пагинацию и размер страницы;
- обновление списка и выбранного ключа;
- выбранный ключ через URL;
- список доступных полей и сохранённую видимость;
- нормализованный статус и бюджетные данные.

### Обязательный паритет нового UI

Новый UI поддерживает все поля старого списка:

- имя и статус;
- идентификатор ключа;
- команда;
- организация;
- пользователь;
- дата создания;
- создатель;
- дата обновления;
- последняя активность;
- срок действия;
- расход и бюджет;
- общий расход;
- дата сброса бюджета;
- модели и разрешённые маршруты;
- TPM/RPM.

Идентификатор ключа доступен в настройке видимости, но скрыт по умолчанию. Это сохраняет ранее выбранный дизайн без потери функциональности.

Статусы `active`, `expired`, `blocked`, `SCIM blocked` и `deleted` не объединяются. Новый UI показывает те же пояснения статуса, наследуемые ограничения бюджета и ссылки на связанные команду и организацию, что и старый UI.

Создание, просмотр, редактирование, перевыпуск и удаление ключа выполняются общими компонентами. Новое upstream-поле бюджета конечного пользователя появляется в обоих интерфейсах через общую форму, без отдельной реализации для «Фокус».

## Модели и эндпоинты

### Общий каркас возможностей

Общий реестр разделов определяет название, право доступа и функциональную панель. Оба интерфейса используют один реестр и не заводят собственные списки вкладок.

Обязательные разделы:

- все модели;
- добавление модели;
- Auto-Routers;
- LLM Credentials;
- Pass-Through Endpoints;
- Health Status;
- Model Retry Settings;
- Model Group Alias;
- Model Access Group Budgets;
- Price Data Reload.

Права proxy admin, viewer, internal user и team admin вычисляются один раз. Недоступная функция скрыта или заблокирована одинаково в обоих интерфейсах.

### Список моделей

Общий контроллер списка моделей отвечает за:

- режим «мои/командные» и «все модели»;
- команду;
- публичное имя/группу модели;
- access group;
- сортировку;
- пагинацию и размер страницы;
- обновление;
- видимость полей;
- выбранную модель через URL;
- удаление, pause/resume и открытие настроек;
- team drill-in и подсказку доступа через виртуальный ключ.

Старый интерфейс отображает таблицу. Новый отображает карточки и правую панель, сохраняя все перечисленные возможности и серверные параметры запросов.

### Формы и действия моделей

Создание и редактирование используют общие схемы полей, provider metadata, нормализацию значений и построитель payload. В общий набор входят базовые поля, существующие credentials, Team BYOK, access groups, guardrails, tags, vector stores, custom pricing, PTU, cache pricing, pass-through, cache-control injection points, дополнительные LiteLLM-параметры и model info.

Auto-Routers используют upstream-компоненты и актуальные классификаторы, включая новые конфигурации, а не копию формы внутри нового UI.

LLM Credentials используют общий контроллер списка, общую форму provider fields, одинаковые правила маскирования секретов и одинаковые create/update/delete операции. Две страницы могут иметь разные карточки и пустые состояния.

Остальные разделы подключают существующие upstream-панели через общий реестр. Пустые вкладки в новом UI запрещены.

## Компоновка нового UI

Для виртуальных ключей сохраняется утверждённая компоновка:

- без выбранного ключа список занимает всё свободное место;
- после выбора справа открываются детали;
- на desktop детали получают больше ширины, чем список, в пропорции 60/40;
- правая панель имеет фиксированную ширину в рамках desktop layout;
- бургер содержит «Виртуальные ключи» и «Модели и эндпоинты»;
- светлая и тёмная темы, а также RU/EN сохраняются.

Для моделей сохраняются карточки слева и детали справа. Общие feature panels размещаются внутри оболочки «Фокус» без возврата внешнего вида старого LiteLLM.

## Синхронизация с upstream

Новая возможность считается перенесённой, когда она добавлена в общий реестр, контроллер или общую форму. Отдельные копии для старого и нового UI не допускаются.

При следующем merge проверяется изменение общих feature panels и реестра. Если upstream добавляет вкладку, поле, действие или permission gate на одной из двух страниц, новый UI получает её через тот же общий контракт.

## Проверка результата

Новые тестовые файлы не создаются по указанию пользователя. Используются существующие проверки проекта и ручная приёмка.

Обязательные автоматические проверки:

- EN/RU parity и аудит пользовательских строк;
- существующие тесты затронутых страниц и общих компонентов;
- lint;
- TypeScript typecheck;
- production build dashboard;
- полная пересборка `litellm/proxy/_experimental/out`;
- отсутствие unmerged paths и конфликтных маркеров.

Обязательная браузерная приёмка проводится для старого и нового маршрута каждой страницы. Для каждой функции проверяются одинаковые данные, доступность по ролям, сетевой запрос и результат действия. Успешный HTTP-ответ без проверки отображения не считается приёмкой.

## Критерий готовности

Работа завершена, когда составлена и закрыта матрица соответствия «возможность старого UI -> общий контракт -> старый renderer -> renderer Фокус» для всех функций двух страниц, все вкладки нового UI содержат рабочие панели, обязательные проверки проходят, а браузерная приёмка не выявляет функциональных расхождений.
